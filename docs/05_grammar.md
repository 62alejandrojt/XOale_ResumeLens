# Stage 4 - Candidate Profile Language (Context-Free Grammar with textX)

Files: `src/candidate.tx` (grammar) and `src/profile_language.py` (generation and validation)

## Purpose

Stages 1-3 produce information about the candidate: personal data, normalized
skills and the result of each profile. This stage defines a small
**domain-specific language (DSL)** that fixes *how* that information must be
written. A profile is accepted only if it follows the lexical and syntactic
rules of the grammar. A valid profile is the input of the visualization stage.

## Example of a valid profile

```
// candidate profile generated by ResumeLens
candidate "Wednesday Addams" {
    contact {
        email: wednesday.addams@example.com
        phone: +57 300 123 4567
        location: "Nevermore Academy, Jericho"
    }
    summary: "3 years of experience developing web applications."
    experience {
        job "Web Application Developer" at "Nevermore Academy Projects" years: 3
    }
    education {
        degree "B.Sc. in Computer Science" at "Nevermore Academy"
    }
    skills {
        JAVASCRIPT REACT NODE_JS POSTGRESQL GIT REST_API
    }
    evaluation {
        profile FULL_STACK_DEVELOPER: ACCEPTED
        profile MACHINE_LEARNING_ENGINEER: REJECTED
        profile DEVOPS_ENGINEER: REJECTED
        profile DATA_ANALYST: REJECTED
    }
}
```

## Grammar in EBNF

Notation: `"x"` is a literal terminal, `[ x ]` optional, `{ x }` zero or more,
`x { x }` one or more, `|` alternative.

```ebnf
CandidateProfile = "candidate" STRING "{"
                       Contact
                       [ "summary" ":" STRING ]
                       [ Experience ]
                       [ Education ]
                       Skills
                       Evaluation
                   "}" ;

Contact     = "contact" "{"
                  "email" ":" EMAIL
                  [ "phone" ":" PHONE ]
                  [ "location" ":" STRING ]
              "}" ;

Experience  = "experience" "{" Job { Job } "}" ;
Job         = "job" STRING "at" STRING "years" ":" INT ;

Education   = "education" "{" Degree { Degree } "}" ;
Degree      = "degree" STRING "at" STRING ;

Skills      = "skills" "{" { SKILL_NAME } "}" ;

Evaluation  = "evaluation" "{" Result { Result } "}" ;
Result      = "profile" PROFILE_NAME ":" STATUS ;

PROFILE_NAME = "FULL_STACK_DEVELOPER" | "MACHINE_LEARNING_ENGINEER"
             | "DEVOPS_ENGINEER" | "DATA_ANALYST" ;
STATUS       = "ACCEPTED" | "REJECTED" ;
```

Lexical rules (terminals defined with regular expressions):

```
EMAIL      = [A-Za-z0-9._%+-]+ @ [A-Za-z0-9.-]+ \. [A-Za-z]{2,}
PHONE      = \+? [0-9] [0-9 -]{6,} [0-9]
SKILL_NAME = [A-Z] [A-Z0-9_]*
STRING     = text between double quotes          (textX built-in)
INT        = [0-9]+                               (textX built-in)
COMMENT    = // until the end of the line         (ignored)
```

## Terminals and non-terminals

**Non-terminals (V):** CandidateProfile (start symbol), Contact, Experience, Job,
Education, Degree, Skills, Evaluation, Result.

**Terminals (Σ):**

- Keywords: `candidate`, `contact`, `email`, `phone`, `location`, `summary`,
  `experience`, `job`, `at`, `years`, `education`, `degree`, `skills`,
  `evaluation`, `profile`.
- Punctuation: `{`, `}`, `:`.
- Fixed values: `FULL_STACK_DEVELOPER`, `MACHINE_LEARNING_ENGINEER`,
  `DEVOPS_ENGINEER`, `DATA_ANALYST`, `ACCEPTED`, `REJECTED`.
- Token classes: `STRING`, `INT`, `EMAIL`, `PHONE`, `SKILL_NAME`.

`PROFILE_NAME` and `STATUS` are written as rules in textX, but they only
choose between fixed words, so they behave as terminals.

**Start symbol:** CandidateProfile.

## Structural characteristics

- **Nested blocks.** The language uses `{ }` blocks inside the main
  `candidate` block. Balanced and nested braces are the reason a context-free
  grammar is needed: this structure cannot be described by a regular expression.
- **Fixed order.** Blocks must appear in this order: contact, summary,
  experience, education, skills, evaluation. A profile with blocks in another
  order is rejected.
- **Required and optional parts.** `contact` (with `email`), `skills` and
  `evaluation` are required. `summary`, `experience`, `education`, `phone` and
  `location` are optional.
- **Repetition.** `Job`, `Degree` and `Result` use one-or-more repetition, so a
  candidate can have several jobs, several degrees and one result per profile.
  `SKILL_NAME` uses zero-or-more, so the skills block can be empty when no
  skill was recognized.
- **Lexical control.** The email, phone and skill names must match their
  regular expressions. Skill names must be canonical (uppercase), the same
  alphabet used by the transducers and automata.

## Extra (semantic) rules

Some rules cannot be expressed with a context-free grammar. They are checked in
`check_rules()` after parsing:

- A skill cannot appear twice in the `skills` block.
- A profile cannot be evaluated twice in the `evaluation` block.

## Validation examples

| Input | Result | Reason |
|---|---|---|
| `tests/profiles/wednesday_addams.cand` | valid | follows all rules |
| profile with only contact, skills and evaluation | valid | other parts are optional |
| `email: john.smith@` | **rejected (lexical)** | does not match EMAIL |
| `skills { sql }` | **rejected (lexical)** | SKILL_NAME must be uppercase |
| `profile DATA_ANALYST: MAYBE` | **rejected (lexical)** | STATUS is ACCEPTED or REJECTED |
| `years: two` | **rejected (lexical)** | INT expected |
| no `evaluation` block | **rejected (syntax)** | required block |
| missing closing `}` | **rejected (syntax)** | unbalanced braces |
| `skills` before `contact` | **rejected (syntax)** | wrong order |
| `profile CHEF: ACCEPTED` | **rejected (syntax)** | unknown profile |
| `skills { SQL SQL }` | **rejected (semantic)** | repeated skill |

textX reports the line and column of the error, for example:
`line 4, col 16: Expected Email`.

## Implementation

- `build_profile_text(data, skills, results)` writes the DSL text from the
  outputs of stages 1, 2 and 3.
- `parse_profile(text)` parses the text with the metamodel built from
  `candidate.tx` and applies the extra rules. It returns the model or raises
  `ProfileError`.
- `validate_profile(text)` returns `(True, "")` or `(False, reason)`.

```
python -m src.profile_language
```

## Limitations

- Strings cannot contain double quotes; they are replaced by single quotes when
  the profile is generated.
- The grammar checks the structure, not if the data is true.
